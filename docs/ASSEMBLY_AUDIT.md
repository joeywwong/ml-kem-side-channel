# Optimized host assembly audit

Inspected with GCC MinGW x86-64 13.2.0, `-std=c99 -O2 -Wall -Wextra
-Werror -fno-lto`. Generated by `python tasks.py bench`. The object disassembly is
recorded in `results/benchmark.json`; `.s`, `.su`, `.o` and executable are under
ignored `build/`. The executable SHA-256 is in the benchmark report.

Both object and **linked benchmark executable** were inspected with `objdump -d`.
`lab_mul` contains zero-extension of the runtime 16-bit inputs, `imul %edx,%eax`,
then constant-division reduction through multiply/shift/subtract and a return.
The final canonical result is in EAX; its upper bits are zero. Thus HW16 of the
canonical result equals HW32 of that register value at this stage, but not HW32
of the unreduced product. This does not assert which stage a physical device leaks.

`lab_masked_mul` contains two distinct calls to `lab_mul`, two 16-bit loads from
the share array and stores of the results. The linked main loop also retains calls
to both variants and consumes their returned values in a checksum. Inputs come
from arrays populated using a runtime argument. `noinline`, separate translation
units and disabled LTO help preserve inspection boundaries; the call graph and
output consumption establish that the computations survived this build. `volatile`
is used only for the final benchmark sink and is not a security guarantee.

| Function/object | Observed host code | Compiler static stack usage |
|---|---:|---:|
| `lab_mul` / baseline.o | 48 byte `.text`, including padding | 8 bytes |
| `lab_masked_mul` / masked.o | 64 byte `.text`, including padding; calls lab_mul | 64 bytes |
| `lab_split`, `lab_recombine` / kernel.o | See full object report | 8 bytes each |

The shared path needs the baseline multiply too (112 bytes combined `.text`
before setup/recombination); it is not just a 64-byte standalone implementation.
GNU `size`'s aggregate `text` column here is **144 / 168 bytes** for baseline /
masked objects because PE sections such as unwind/compiler metadata are included;
do not confuse it with the `.text` section. Static `.su` usage is per function,
including ABI effects, not measured maximum whole-call-chain stack. No heap is
allocated by the scalar functions. Benchmark static arrays and C runtime costs
are not included in those scalar object numbers.

No ARM code was generated: the cross-compiler is unavailable and no MCU memory
map is verified. F030 lowering of `%` may involve a software divide helper;
that must be inspected after compiling the actual target. Host assembly does
not predict ARM timing or leakage. The reuse of registers across share calls
is itself a potential transition-leakage problem excluded by the simple model.
The code is not formally verified, constant-time-certified, or physically masked.
